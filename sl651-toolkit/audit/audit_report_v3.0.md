## 一、结论总览

| 严重度 | 数量 | 编号 | 说明 |
|--------|------|------|------|
| 高（建议优先修） | 1 | M-1 | SL427 实时参数类型表（`CTRL_FUNC_MAP`）与规约 §7.3.22 表33~44 **系统性不符**：7 种参数类型长度/小数位/单位错误；水温完全解不出、水压/电量/蒸发量数值错误；另 0x03 流量/累计水量未按“成对”解析 |

**核心结论**：v1.4.3 对 v2.8 的修复（pH lookup、DIV 异常保护、B1 多记录）质量可靠，全套件 11/11、随机变异零未受控异常。但本轮把审计维度从“v1.4.3 新代码”扩展到“**代码表 vs 规约表**”后，发现项目存在一类此前 20 余轮均未覆盖的系统性问题：

> **多处“协议常量表/特殊标识符语义”不是从规约表逐项推导出来的，而是按实现需要手写的；测试又按实现输出回填，于是实现与测试互相印证、与规约脱节。**

M-1（SL427 类型表）与 M-3~M-5（SL651 特殊标识符）都属于这一类。它们不是崩溃型缺陷，而是**静默错值/静默丢值/不可与第三方互通**，在“只跑自家 11 套件”的回归模式下永远不会被发现。

## 二、问题清单

### M-1（高）SL427 `CTRL_FUNC_MAP` 与规约表33~44 系统性不符

**位置**：`sl427/constants.py:148-170`（`CTRL_FUNC_MAP`）；消费点 `sl427/decoder.py:93-157`（`_parse_ctrl_func_data`）、`:201-232`（`_parse_comprehensive`）、`:1201-1231`（`_parse_b1_records`）

**规约依据**：SL/T 427-2021 §7.3.22 a)~l) 及表33、34、37~44、47；表18（水质参数小数位）

**问题**：类型码 0x07/0x08/0x09/0x0A/0x0B/0x0C/0x0F 的 `byteLen`/`decimal`/`unit` 与规约不符。`_parse_ctrl_func_data` 用 `byteLen` 同时做“切片长度”和“循环步长”，因此长度错误不仅使**本条值错**，还会让它后面的所有数据**整体错位**：

| 类型码 | 代码值 `byteLen/decimal/unit` | 规约值（表号） | 实际后果 |
|--------|------------------------------|----------------|----------|
| 0x07 气象 | 3 / 0 / `""` | **8B**：气压3B + 风速(含风向)3B（BYTE6 高半字节=风向0~8）+ 气温2B（表40） | 只把气压前 3B 当“气象参数”，风速/风向/气温静默丢弃 |
| 0x08 电量 | 3 / 0 / `""` | **4B / 0.01 / kW·h**（表47） | 1234.56 kW·h → `123456`，无单位，第 4 字节丢弃 |
| 0x09 水温 | 3 / 0 / ℃ | **2B / 0.1 / ℃**（表41） | 合法 B0/C0 数据（2B）**一个要素都解不出**（3B>2B 直接返回 `[]`，无 warning） |
| 0x0A 水质 | 3 / 0 / 有符号数组 | **4B/参数、小数位随参数**（表18、§7.3.22 i)）；B0 还有 5B 位图 | 把位图当数值、每 3B 一错位；多参数整体错位 |
| 0x0B 土壤含水率 | 3 / 0 / % | **4B**：含水率2B + 采集深度2B（表42） | 3B 拼成一个无意义百分数，深度丢失、后续错位 |
| 0x0C 蒸发量 | 3 / 0 / mm | **3B / 0.1 / mm**（表43） | 123.4mm → `1234`（10 倍） |
| 0x0F 水压 | 3 / 0 / **MPa** | **4B / 0.01 / kPa**（表44） | 1234.56kPa → `123456 MPa`（数值 100 倍且单位错） |

对照：0x01~0x06 的 `byteLen/decimal` 与规约一致；0x0D/0x0E 是“同码不同义”的上下文类型，代码有专门分支（B0 综合参数 / C0 统计雨量 / 84H 电压），不按该表通用解析。问题集中在“非水位/雨量/流量”的其余类型——恰好是真实水资源监测站最常用的一批（水温、水质、水压、电量、土壤含水率）。

**实测（构造合规数据）**：

```python
from sl427 import SL427Encoder, SL427Decoder, encode_address
from sl427.constants import make_ctrl
enc = SL427Encoder(encode_address(1, 110000, 1))
dec = SL427Decoder()

# 水温：表41 的合规 2B 数据（个位/十分位=0x23，十位=0x01 → 12.3℃）
r = dec.decode(enc.build_query_response(0x09, bytes.fromhex("2301")))
print([e.name for e in r.elements if e.name == "水温"])      # []  ← 一个都没有

# 水压：表44 的合规 4B 数据（123456 → 1234.56 kPa）
r = dec.decode(enc.build_query_response(0x0F, bytes.fromhex("56341200")))
print([(e.name, e.value, e.unit) for e in r.elements if e.name == "水压"])
# [('水压', '123456', 'MPa')]  ← 数值 100 倍，单位应为 kPa

# 蒸发量：表43 的合规 3B 数据（1234 → 123.4 mm）
r = dec.decode(enc.build_query_response(0x0C, bytes.fromhex("341200")))
# [('蒸发量', '1234', 'mm')]  ← 10 倍
```

**影响范围**：

- AFN=B0 查询响应（`decoder.py:1309-1330`）：水温丢值，水压/电量/蒸发量错值，气象/水质/土壤错位；
- AFN=C0/81/82 自报（`decoder.py:1267-1308`、`:1338-1382`）：同上；
- AFN=B1 固态存储（`:1201-1231`）：按同一错误 `byteLen` 逐条切片，整段记录错位；
- AFN=B0/FF 综合参数（`:201-232`）：`COMP_BITS` 中 0x0A/0x0B/0x07 的长度错误，只要这些 bit 置位，后续参数块全部错位；
- `_parse_ctrl_func_data` 对“数据短于 `byteLen`”是**静默返回 `[]`**，没有 warning——这正是 0x09 水温“消失”而无人察觉的原因。

**修复建议**：

1. 按 §7.3.22 表33~44 重写 `CTRL_FUNC_MAP` 的 `byteLen/decimal/unit/signed/array`；0x09/0x0C/0x0F/0x08 可先按标量修正，0x07/0x0A/0x0B 需要**专用解析器**：
   - 0x07 气象：气压 3B + 风速(含风向) 3B（BYTE6 高半字节=风向 0~8）+ 有符号气温 2B，共 8B，拆成 4 个值（气压/风速/风向/气温）；
   - 0x0A 水质：B0 先读 5B 位图，再按表18 逐参数 4B + 各自小数位/单位解析；C0/81/82 的 0x0A 语义需按位图同样处理；
   - 0x0B 土壤含水率：4B = 2B 含水率(0.1%) + 2B 采集深度(cm)，拆成两个要素；
2. `_parse_ctrl_func_data` 在 `len(data) < byteLen` 时写入 warning（“数据不足一个记录，剩余 XB 未解析”），避免再次静默丢值；
3. 增加**表驱动不变量测试**：从 §7.3.22 抄一张 `{func: (byteLen, decimal, unit)}` 的期望表，逐项断言 `CTRL_FUNC_MAP` 与解码输出；对 16 个类型各构造一条合规帧，断言“要素名/数值/单位”三项；
4. 综合参数（`_parse_comprehensive`）建议重构为“按位图先算每块长度，再逐块调用专用解析器”，不要复用标量 `byteLen`。

> **修复护栏（对抗复核补充，防“修错”）**：`COMP_BITS = [0x0A,0x0B,0x06,0x07,0x05,0x03,0x02,0x01]` 的位序（bit0=水质 … bit7=雨量）与表45 **一致**，综合参数的问题只在被引用类型的 `byteLen`，修复时**不要重排位序**。

**补充（0x03 流量/水量的配对语义）**：0x03 的“单个 5B 流量值”格式本身正确（表35），但 §7.3.22 c) 规定流量与累计水量**成对排列**：`流量1(5B) + 累计水量1(5B) + 流量2(5B) + …`，某类不监测时用 `AAAAAAAAAA` 占位（表36）。当前 `_parse_ctrl_func_data(0x03, …)` 把每个 5B 都按流量解析，实测 `流量 12.345 m³/s + 累计水量 1234 m³` 输出为两个“流量/水量”：`12.345 m³/s` 与 `1.234 m³/s`（后者本应是 1234 m³）。若仪表只监测流量，`AAAAAAAAAA` 会被 `_is_fill` 识别为缺测并输出一个 `-`（尚可）；两类都监测时必错。综合参数（表45）中的流量位也应按 10B 块计。建议为 0x03 增加“流量/累计水量成对”解析分支，或在 `_parse_ctrl_func_data` 中按“每 10B 一组”分派。**注意**：累计水量必须按表36 单独解码（BYTE5 = 0B + 十亿位/亿位 BCD），不能复用 `_parse_flow` 的表35 符号/单位位解释，否则 BCD 数字会被误读为符号/单位。

### M-2（中）SL427 上行统计雨量：数值缩小 10 倍、类型标签错误、且完全没有测试

**位置**：`sl427/decoder.py:235-256`（`_parse_statistical_rainfall`）；调用点 `:1206`、`:1280`、`:1299`、`:1355`、`:1373`

**规约依据**：SL/T 427-2021 §7.5.6 c) + 表54；3B 雨量数据格式见 §7.3.22 a) 表33（BYTE1 个位/十分位，BYTE2 百位/十位，BYTE3 万位/千位；0.1mm）

**问题 1：数值 /100 应为 /10。**
表33 的 3B 小端 BCD 解码结果是以 **0.1mm** 为单位的整数，除以 10 才是 mm。代码 `v / 100` 使所有统计雨量缩小 10 倍。

**问题 2：类型字节按枚举 `{0x00..0x04}` 解释。**
表54 的类型字节是位域：`D7~D6` = 类别（00 时段、01 小时、10 日、11 测试），`D5~D0` = 时段长度（步长分别为 5min/1h/1d）。代码把 0x00 映射“本次”、0x01“小时”、0x02“日”、0x03“月”、0x04“年”，对真实类型（如 0x41 = 小时 1、0x81 = 日 1、0xC0 = 测试/累计）全部落空，显示为“类型0x41”。

**实测**：

```python
# 类型 0x41 = 01 000001B = 小时降雨量，时长 1h；雨量 12.3mm 的合规 3B 为 23 01 00
frame = enc.build_self_report_c0(0x0E, bytes.fromhex("41230100"),
                                 tp=datetime(2026, 7, 1, 6, 0))
r = dec.decode(frame)
print([(e.name, e.value) for e in r.elements if "雨量" in e.name])
# [('统计雨量(类型0x41)', '1.23')]   ← 应为 12.3mm / 小时降雨量(1h)
```

**测试现状**：全仓库 `grep 统计雨量` 在 `tests/` 下 **0 命中**——v2.0 M-3 的修复从未被回归测试覆盖；`test_protocol_contracts.py:139` 只测 B0 的 0x0E（综合参数），不覆盖 C0/81/82/B1 的 0x0E（统计雨量）。

**修复建议**：

1. 数值改为 `v / 10`、1 位小数；
2. 类型按位域拆解，显示如“时段降雨量(3×5min)”“小时降雨量(1h)”“日降雨量(1d)”“测试/累计雨量”；
3. 补 4 类各一条用例（0x00/0x41/0x81/0xC0 或 0x03/0x42/0x82/0xC0），断言数值 12.3 与名称；
4. 顺带修 C0/81/82/B1 四个入口共用同一函数的问题（目前是优点），确保只改一处。

### M-3（中）SL651 人工置数报 F2 定义符：编码器缺写、解码器把定义符当载荷（双向不互通）

**位置**：`sl651/encoder.py:494-502`（`build_manual_frame`）、`sl651/decoder.py:1021-1036`（`_parse_elements` 的 F2 分支）；文档 `docs/project.md:94,170`、`README.md:307`

**规约依据**：SL651-2014 6.6.3.2 表26（标识符 = 引导符 1B + 定义符 1B）；表C.1 注 c：“HEX/BCD 编码时数据定义字节固定用 **F2H** 表示”；6.6.4.8 表38

**问题**：

- 真实帧是 `F2 F2 + SL330 载荷`（第一个 F2 引导符、第二个 F2 固定定义符）；
- 解码器在读完 F2 引导符后**没有读定义符**，直接把第二个 F2 算进载荷：福建样本 `F2F25120312E323334` 被解成 8 字节 `F25120312E323334`，正确载荷应为 7 字节 `5120312E323334`；
- 编码器 `build_manual_frame(payload)` 产出 `F2 + payload`，**少了定义符 F2**。第三方按规约解码时会把载荷首字节 `0x51` 当定义符（声明 10B/1 位小数），随后只按 6B 解析，载荷被截断/错位；
- 本工具编码→解码“自洽”，所以自家测试通过；与真实设备/第三方工具**双向都不通**；
- v2.3 M-3 当时给出的两个方案（“编码器补定义符”或“解码器按剩余全部字节”）中，实现选了后者但**连定义符一起算进了载荷**，且测试按此回填，形成“测试锁定错误”。

**实测**：

```python
payload = bytes.fromhex("5120312E323334")          # SL330 的 "Q 1.234"
f = enc.build_manual_frame(payload)
print(f[22:-3].hex().upper())                       # F25120312E323334  ← 缺第一个 F2
r = SL651Decoder().decode(bytes.fromhex(
    "7E7E0110000000060000350011022F7D221205102729F2F25120312E32333403BF56"))
print(r.elements[0].raw)                            # F25120312E323334  ← 多了一个 F2（应为 5120312E323334）
```

**修复建议**：

1. **编码器**：`build_manual_frame` 改为 `bytes([0xF2, 0xF2]) + payload`（或复用 `build_frame(0x35, b"\xF2\xF2" + payload)`）；
2. **解码器**：F2 分支先读定义符并校验等于 `0xF2`（不等则 warning + 兼容旧口径），载荷取定义符之后的全部字节；
3. 修正 `docs/project.md` §2.2/§2.6、`README.md` 的“F2 后无定义符”表述，以及 `examples/fujian_messages.txt` 相关注释（如需要）；
4. 测试改为断言 `raw == "5120312E323334"`（与福建样本一致），并增加“编码器输出以 F2F2 开头”的断言；
5. 同理检查 **F3/FD**（见 M-5）：它们与 F2 是同一类“固定定义符 + 变长载荷”的语义。

### M-4（中）SL651 下行配置/查询帧：附录D 参数标识符的定义符缺失或恒 0

**位置**：`sl651/encoder.py:385-392`（`build_query_body`，3AH）、`:462-470`（`build_read_config_frame`，41H/43H）、`:472-478`（`build_init_solid_storage`，47H）、`:480-492`（`build_change_password_frame`，49H）、`:519-522`（`build_reset_frame`，48H）

**规约依据**：SL651-2014 6.6.3.2 表26（标识符恒为 2 字节：引导符 + 定义符）；6.6.3.4（参数标识符引导符见附录D）；福建省水文监测数据接入规定 V1.0 §7.2.3（3AH）、§7.3.1（41H）、§7.3.2（43H）、§7.3.7（47H）、§7.3.8（48H）、§7.3.9（49H）的报文示例

**问题**：这 6 个方法产出的正文与规约/福建示例不一致：

| 方法 | 当前正文（实测） | 规约/福建示例 | 偏差 |
|------|------------------|----------------|------|
| `build_init_solid_storage()` | `97` | `97 00` | 缺定义符 0x00 |
| `build_reset_frame()` | `98` | `98 00` | 缺定义符 0x00 |
| `build_change_password_frame(0,0x4D2)` | `03 0000 03 04D2` | `03 10 0000 03 10 04D2` | 两处各缺定义符 `10`（2B/0 位小数） |
| `build_query_body([0x26])`（3AH） | `26 00` | `26 19` | 定义符应为该要素的数据定义（3B/1 位小数） |
| `build_read_config_frame([1,2,3])`（41H） | `01 00 02 00 03 00` | `01 20 02 28 03 10` | 定义符应为参数自身长度（4B/5B/2B） |
| `build_read_config_frame([0x20,0x23])`（43H） | `20 00 23 00` | `20 08 23 10` | 同上 |

**根因**：`build_query_body` 的注释“查询时数据域长度为 0”把**定义符的“数据长度”语义**误当成“本次不编数据，所以定义符=0”。定义符描述的是**该参数/要素的数据定义**（长度+小数位），与本次帧里是否携带数据无关；47H/48H 的“无数据参数”定义符则固定为 0x00。49H 更是绕过了 `_make_def_byte` 直接拼字节，形成第二个“同源判定未单点实现”的入口。

> **历史审计说明**：v2.6 曾以“6.6.3.2 标识符=2 字节”为依据判定“定义符数据长 0 符合规约”（v2.6 报告 §三表）。该判定只看了“2 字节”这一半，漏了“定义符描述该参数自身数据定义”这另一半；本轮以福建示例（`26 19`、`01 20 02 28 03 10`、`20 08 23 10`）证明 0 是错的。这也是本项目“静态对照表”被误读的典型：**规约的每条都要在真实样本上闭合**。

**影响**：按规约实现的 RTU 在收到这些下行帧时，可能把定义符 0 解释为“0 字节参数”而拒绝/回 0 值，或把 49H 的 `00` 当成定义符导致新旧密码错位——**控制类命令（初始化、恢复出厂、改密、读取配置）可能整体失效**。这类帧通常由本工具生成、再人工比对，故不易在自家测试中暴露（测试只断言 CRC/功能码/方向，不断言正文）。

**实测**：

```python
e = SL651Encoder(center_addr=0x10, station_addr="0000000006", password=0x04D2, station_type=0x48)
print(e.build_init_solid_storage()[22:-3].hex().upper())                 # 97
print(e.build_reset_frame()[22:-3].hex().upper())                        # 98
print(e.build_change_password_frame(0, 0x4D2)[22:-3].hex().upper())      # 0300000304D2
print(e.build_query_body([0x26]))                                        # b'&\x00'
print(e.build_read_config_frame([1, 2, 3])[22:-3].hex().upper())         # 010002000300
```

**修复建议**：

1. **49H**：直接复用 `build_set_param_frame([(0x03, old, 2, 0), (0x03, new, 2, 0)], function_code=0x49)`，由 `_make_def_byte(2,0)=0x10` 自动生成 `03 10 xxxx`，消除手写字节；
2. **47H/48H**：正文改为 `b"\x97\x00"` / `b"\x98\x00"`；
3. **3AH/41H/43H**：API 不能只收 `guides`。建议：
   - 3AH 改为 `list[tuple[int,int,int]]`（引导符、数据字节数、小数位），或从表 C.1 的 `N(D,d)` 建一张 `{guide: (len,dec)}` 查询表；
   - 41H/43H 从附录D 表 D.1/D.4 建 `{param_guide: (len,dec)}` 表（01H=4/0、02H=5/0、03H=2/0、**20H=1/0**、**23H=2/0** 等；注意 20H 是 N(2) 即 1 字节/def=0x08，不是 3 字节），按参数查表生成定义符；更推荐按 `N(D,d) → 字节数 = ceil(D/2)、小数位 = d` 的换算规则从表D.1/D.4 自动推导，天然避免手抄笔误；
4. **测试**：把福建示例 47H/48H/49H/3AH/41H/43H 的**正文逐字节**写成 fixture，断言编码器输出等于示例正文（至少断言标识符段），而不是只断言 CRC。现有 `tests/test_sl651.py:1196/1201` 断言的恰恰是错误正文，需要一并改。

### M-5（中）SL651 图片（F3）/批量数据（FD）：固定定义符被当作“长度”，剩余数据被解析成伪要素

**位置**：`sl651/decoder.py:1192-1201`（`dt == "RAW"`，FD）、`:1203-1213`（`code == "f3"`）；定义符解析在 `:1040-1043`

**规约依据**：SL651-2014 表C.1 第 14/15 项 + 注 d/e/f：
- F3H 图片：“标识符之后全是其数据……数据定义字节固定用 **F3H**”；
- FDH 流量（流速）批量数据：“标识符之后全是其数据……数据定义字节固定用 **F6H**”；
- 二者长度“一般超过 32 字节”，**不能**用 5 位定义符表达。

**问题**：解码器对 F3/FD 仍走通用 `parse_def_byte(def_byte)`，把固定定义符 `F3`/`F6` 当成“30 字节 / 3 位小数”或“30 字节 / 6 位小数”，只消费 30B，随后把剩余图片/批量数据当要素继续解析。

**实测（用真实福建 0x36 图片帧的正文拆成 2 个 SYN 包重组）**：

```text
F3 图片信息 <图片数据 30 字节: FFD8FFE0...>     ← 真实图片 220B（body 245B - 23B 头 - 2B 标识符），只显示前 30B
05 时段长 7                                     ← JPEG 续流被解析成伪造要素
```

（原始 0x36 帧共 4 包；单包直解时因 `total>1` 不解析正文，所以既有基线看不到这个问题。）

**影响**：`docs/project.md` §2.2 声称 0x36“解码 ✅”，但实际多包图片（唯一有真实样本的形态）重组后会得到“30 字节图片 + 若干伪要素”；FD 批量流速同理。图片/批量数据虽然不参与数值计算，但伪要素会污染要素列表、误导下游。

**修复建议**：

1. F3/FD 与 F2 采用同一规则：**固定定义符 + 剩余全部为载荷**。在 `_parse_elements` 中对 F3/FD 增加“消费到正文末尾”的分支（类似 F2），并把完整字节数/预览写进 `value`/`raw`；
2. 不要用 `parse_def_byte` 解释 F3/FD 的定义符；在 `constants.py` 中把固定定义符（F2/F3/F6）与数组定长（F4=12/F5~FC=24）分开建模；
3. 补测试：用真实 0x36 的 4 包数据（或现有单包正文拆 2 包）走 `feed()`，断言“只有 1 个 F3 要素、载荷字节数=正文剩余长度、无其他要素”；
4. **现有 FD fixture 本身也不合规**：`tests/test_constants_spec.py:88` 用 `FD 18`（def=3B）构造批量数据，而注 f 要求固定定义符 **F6H**；修 M-5 时应同步改为 `FD F6`，否则测试会继续固化非规约口径；
5. 若担心厂商把 F3 当长度用，可在定义符≠固定值时写 warning 并降级，而不是静默按 30B 解析。

### L-1（低）SL651 下行配置帧解码：把附录D 参数当附录C 要素；F1F1 跳过假设导致 49H 密码丢失

**位置**：`sl651/decoder.py:1004-1151`（`_parse_elements`）、`:1053-1054`（F1F1 跳过 12 hex）、`:688-691`（下行方向进入 `_decode_binary`）

**问题**：

1. 下行 40H~43H/47H~49H 的正文是**附录D 参数标识符**（0x01 中心站地址、0x02 遥测站地址、0x03 密码……），与附录C 要素引导符**编码空间重叠但语义不同**。`_parse_elements` 只用 `SL651_ELEMENTS`，于是：
   - 41H 示例正文 `01 20 02 28 03 10` → 解出“断面面积 = 2280310 m²”（把 4B 数据 `02 28 03 10` 当面积）；
   - 49H 下行 `03 10 0000 03 10 04D2` → 解出“瞬时水温 = 0 / -”。
2. F1F1 跳过固定按“站码 5B + 站类 1B”处理；但 49H 上行响应（表66）是 `F1F1 + 站码5B + 新密码(03 10 + 2B)`，没有站类字节。跳过时把密码标识符 `03` 当站类吃掉，随后错位，最终**新密码不显示**（福建 49H 样本实测 0 要素）。

**影响**：下行/响应帧的要素列表是“看起来像真数据”的错误结果（比不显示更危险）；49H 的设置结果无法从解码器确认。不影响上行遥测主路径。

**修复建议**：

1. 对下行 40H~43H、47H~49H（以及 49H 上行响应）走**附录D 参数表**，或至少在 `function_code in (0x40..0x43,0x47..0x49)` 时不套用 `SL651_ELEMENTS`，改为“参数标识符 + 原始值”展示；
2. F1F1 跳过改为“按 function_code 选择结构”：通用上行（F0F0 存在）站类 1B；49H 响应无站类；或先探测 F0F0 是否存在再决定跳过长度；
3. 补测试：41H/49H 示例帧断言“不出现与要素表同名的伪造要素”，49H 响应断言“新密码=0x04D2”。

### L-2（低）SL427 59H/5AH 水质参数：值未按表18 小数位缩放、无单位

**位置**：`sl427/decoder.py:415-437`（`_parse_water_quality_427`）

**规约依据**：SL/T 427-2021 表18（D0 水温 N(3,1)℃、D1 pH N(4,2)、D2 溶解氧 N(4,2)mg/L、D3 电导率 N(5)μS/cm、D7 总磷 N(5,3)、…）

2. `_parse_water_quality_427` 按 bit 取 decimal/unit，值输出 `f"{v/10**d:.{d}f}"`；
3. 测试断言“水温 123.4℃ / 溶解氧 56.78 mg/L”，而不是原始整数 1234/5678（`tests/test_sl427_query_afn.py:204` 目前断言的正是错误值）。

### I-1（提示）A1H 数据域长度：规约自身“30 字节”与“15 个参数×2B”矛盾

**位置**：`sl427/encoder.py:654-670`（`build_set_report_kinds`）、`sl427/decoder.py:497-516`（53H）、`:713-729`（A1H 响应）

**问题**：§7.2.23 写“数据域为 30 字节”，但 b) 又列了 15 个参数（雨量…图片）每参数 2B，合计应为 32B；按 30B 只能容纳 14 个间隔。编码器当前允许 1~15 项、按 `2+2N` 变长输出（测试只用 2 项 → 6B），与“固定 30B”口径不一致；解码器按实际长度解析。

### 5.5 M-5（真实 0x36 重组）

```python
from sl651.crc import crc16
from sl651 import SL651Decoder
from sl651 import constants as C

line = [l.strip() for l in open("examples/fujian_messages.txt")
        if l.strip() and not l.startswith("#")
        and l.startswith("7E7E011000000006000036")][0]
orig = bytes.fromhex(line)
hdr_base = bytearray(orig[:13])                     # 7E7E + 11B 头
body = orig[17:14 + ((orig[11] << 8) | orig[12])]   # 去掉 3B 包头的真实正文
mid = len(body) // 2
frames = []
for i, ch in enumerate([body[:mid], body[mid:]], 1):
    blen = 3 + len(ch)
    hdr = bytearray(hdr_base)
    hdr[11], hdr[12] = (blen >> 8) & 0xFF, blen & 0xFF
    pkt = bytes([0x00, 0x20, i])                    # total=2, seq=i（12 位+12 位）
    frame = bytearray(hdr) + bytes([C.SYN]) + pkt + ch \
            + bytes([C.ETB if i < 2 else C.ETX])
    frame += crc16(bytes(frame)).to_bytes(2, "big")
    frames.append(bytes(frame))

d = SL651Decoder(); out = []
for f in frames:
    out += d.feed(f)
m = out[0]
print(m.reassembled, len(m.elements))               # True 2
print([(e.code, e.name, str(e.value)[:30]) for e in m.elements])
# [('F3', '图片信息', '<图片数据 30 字节: FFD8FFE0...>'),
#  ('05', '时段长', '7')]   ← F3 只取 30B，剩余 JPEG 被当成要素
```

## 六、审计师结论

1. **项目工程质量高**：异常契约、分帧重组、脱敏、缓存上限、真实语料基线、变异测试都明显优于同类工具；v1.4.3 的修复也经得起运行时复核。
2. **但“规约表驱动”这一维度长期缺位**：`CTRL_FUNC_MAP`、附录D 参数定义符、F2/F3/FD 固定定义符这几处，都是“按实现写常量/按实现回填测试”，与规约的真实语义存在系统性偏差。它们不会让测试变红，却会让工具在与真实 RTU/第三方中心站对接时出错——这正是本轮 1 高 + 4 中的核心价值。
3. **建议把“规约表核对”固化为发版门禁**：至少包括 SL427 表33~44 的类型表、SL651 表C.1 注 a~g 的特殊标识符、附录D 参数定义符；期望值从规约/真实样本抄，不从实现输出抄。
4. 本报告所有结论均可在 v1.4.3 工作区复现；修复时建议先加红测试（§5 构造），再改实现，最后核对福建/北京基线是否需要同步更新。

## 七、对 v2.9 报告（`audit/audit_report_v2.9.md`）的复核意见

> v2.9 是上一轮针对 v1.4.3 diff 的审计，结论为“v2.8 五项全部闭环 + 新增 1 Low（静默截断未外推）”。本轮对它的复核结论：**方法可靠、L-1 成立；但“0 Medium / 无数据正确性风险”只在其自述的窄范围内成立，不能作为项目级结论；另有两处结论需要修正。**

### 7.1 成立且已独立复现的部分

- **v2.8 五项闭环**的运行时验证（pH casefold、DIV 受保护入口、B1 多记录、B1 时间、docstring）：本轮复核一致，✅；
- **L-1（静默截断）**：独立复现成立——
  ```text
  B0/0x01 两条雨量（001000 002000 + 4B 状态）→ 仅 1 条“100.0”，无 warning；
  同一帧 0x02（数组型）两条水位 → 两条都展开；
  AFN=64 body 7B → 1 条“流量上限[1]”，尾随 2B 静默丢弃。
  ```
- **强变异手法（先破坏 payload 再编码、保持 CRC 有效）**：方法正确，本轮复跑结果同为 0 未受控异常；
- **R-1~R-6** 的遗留判断基本准确；R-6“不可达死分支”复核无误。

### 7.2 需要修正/加强的结论

1. **“文档一致性全部核对通过”不成立（过度声明）**：
   - `docs/handoff_main.md:34` 仍写 `__version__ = "1.4.0"`，实际为 1.4.3；
   - `docs/project.md:38` 仍写“7 个辅助套件”，实际为 10 个辅助套件（总 11 套件）；
   - `docs/handoff_test.md` 的 §4.3/§8 与第 45/218 行仍是 v1.3 时代的“57 项”和遗留列表（含“0x0D 上行=雨量”这种已被表6 否定的表述）。
   v2.9 的核对只覆盖了“文件头的基线版本”和“各文件 `def test_` 计数”，没有覆盖正文中的版本串与计数描述。

2. **R-7“0x0E 跨 AFN 语义差异属规约本身、无需改动”结论过强**：
   - “B0 用综合参数、C0/B1 用统计雨量”的**分支判断**是对的；
   - 但 v2.9 没有继续审计 `_parse_statistical_rainfall` 的实现，而该函数恰有数值 `/100`（应 `/10`）与类型枚举（应为 D7~D6 类别 + D5~D0 时长）两处错误（见本报告 M-2）。因此“无需改动”不成立；应改为“分支正确，但统计雨量解析待修”。

3. **“仅新 Low、无数据正确性风险”的适用范围**：
   - 对 v1.4.3 的 diff 而言成立；
   - 对项目整体不成立：本报告 M-1（7 类参数长度/小数位/单位）、M-2（统计雨量 10×）、M-3~M-5（F2/F3/FD、附录D 定义符）都是数据正确性/互通性问题，且均在 v2.9 的“Layer 1 限本轮变更范围”之外。v2.9 报告自身已声明范围，但汇总句容易被读成“项目健康”，建议在报告头/结论中显著标注“本结论仅覆盖 v1.4.3 diff，不代表规约符合性”。

4. **v2.9 的 L-1 与本报告 M-1 有交叉但不同根**：
   - v2.9 L-1 是“多记录/尾随字节无 warning”，属“留痕”问题；
   - 本报告 M-1 的 0x03 配对问题（流量+累计水量）是“语义错位”，不是留痕问题；两者应分别修复，不能因为 L-1 是 Low 就忽略 M-1 的 0x03。
