| 类别 | 数量 | 说明 |

**核心结论**：
1. 主测试套件 24/24 通过、福建 23 条/北京 25 条真实报文 CRC 全通过——**但这仅证明 HEX/BCD 上行链路自洽**。本次审计将验证范围扩展到**规范规定的另一种编码制式（ASCII 帧）与下行控制帧正文结构**，发现 2 项严重、12 项中等缺陷，全部是"自产自销往返测试"无法暴露的互通性问题。

5. v1.7/v1.8 已修复项（模拟器引擎、小时报 12 组校验、充值量小端）经复测保持有效 ✅。

## 二、严重缺陷（Critical）

### [C-1] SL651 ASCII 编码帧为私有方言，与规范表16/17 完全不符

**规范依据（原文核对）**：

表16《ASCⅡ字符编码 M1/M2/M4 模式上行帧结构定义》（规范文本 830~888 行）：

| 序 | 字段 | 传输字节数 | 说明 |
|----|------|-----------|------|
| 1 | 帧起始符 | **1** | SOH（**单字节 01H**） |
| 2 | 中心站地址 | 2 | 1 字节 HEX **转换为 2 个 ASCⅡ字符**传输 |
| 3 | 遥测站地址 | 10 | 转换为 **10 个 ASCⅡ字符**传输 |
| 4 | 密码 | 4 | 2 字节 HEX 转换为 **4 个 ASCⅡ字符** |
| 5 | 功能码 | 2 | 1 字节转换为 **2 个 ASCⅡ字符** |
| 6 | 报文上下行标识及长度 | 4 | 2 字节 HEX 转换为 **4 个 ASCⅡ字符**；第 1 字符为方向（0 上行/8 下行），其余 3 字符为正文长度 |
| 10 | 校验码 | 4 | 2 字节 HEX 转换为 **4 个 ASCⅡ字符**；高位在前 |

即规范 ASCII 帧是**全字符帧**：除 SOH/STX/ETX 控制字符外，头部每个字段都是 HEX 字符文本，CRC 也是 4 个字符。

**代码实现**：

```python
# sl651/decoder.py:246-247 —— 要求双字节 0101 起始
if cleaned[:4].upper() not in ("7E7E", "0101"):
    raise DecodeError("报文不是以 7E7E(HEX/BCD) 或 0101(ASCII) 开头")

# sl651/encoder.py:105-111 —— ascii_mode 仅替换起始符，头部仍为二进制
start_byte = C.SOH if ascii_mode else C.START_BYTE
frame_body = bytes([start_byte, start_byte]) + bytes(header_body)   # 01 01 双字节
crc = crc16(frame_body)                                             # 2 字节二进制 CRC
```

差异清单：

| 项目 | 规范表16/17 | 代码实现 |
|------|-------------|----------|
| 起始符 | SOH ×1（01H） | SOH ×2（01 01） |
| 中心站址/站址/密码/功能码/长度 | ASCⅡ字符（2/10/4/2/4 字符） | 二进制字节（1/5/2/1/2 字节） |
| 正文站码/观测时间标识 | ASCII 标识符 ST / TT（附录C） | 字符串 "F1F1" / "F0F0"（`encoder.py:294-297`） |
| CRC | 4 个 ASCⅡ字符 | 2 字节二进制 |

**构造性验证（已执行）**：按表16 构造合规 ASCII 帧（单 SOH + 字符头 + `ST 00418D2337 48 TT ...` 正文）送解码器：

```
解码拒绝: 报文起始符应为 02H(STX) 或 16H(SYN)，实际 53H
```

（53H 即字符 'S'——解码器把第 2 字节 01H 当作中心站址后整体错位。）

**影响**：凡按 SL651-2014 表16/17 实现的设备或中心平台发出的 ASCII 帧，本工具**一律无法解码**；本工具编码的"ASCII 帧"也无法被合规对端识别。需求 §2.5"自动识别 0101(ASCII)"、§2.6 `build_ascii_frame` ✅、P2"ASCII 编码帧支持 ✅"三项声称实际指向同一私有方言；`test_sl651_ascii` 为编码器→解码器自产自销往返，不能证明规范符合性。

**修复方向**（仅供参考）：ASCII 模式按表16/17 重构——单 SOH 起始，头部各字段以 HEX 字符文本传输，正文标识符用 ST/TT，CRC 以 4 字符传输。

### [C-2] SL427 AFN=81H 自报告警帧数据域顺序错误

**规范依据（7.5.2 b，原文 1450~1452 行）**：

> 随机自报帧的数据域中**前 2 个字节为报警状态**，**最后 2 个字节为终端机状态**，Tp 为报警时间……当报警参数为水位、水压、流量和水质时**中间字节为实时参数值**。

即 81H 数据域布局为：`报警(2B) + [参数值] + 状态(2B) + Tp(7B)`——报警字在参数值**之前**，与 C0H（7.5.6 b："数据域最后 4 个字节是终端机报警状态和终端机状态"）布局相反。

**代码实现**：

```python
# sl427/encoder.py:152-154（81H 与 C0/82 共用同一顺序）
payload = bytearray(data)                    # 参数值在前
payload.extend(alarm.to_bytes(2, "little"))  # 报警在后
payload.extend(state.to_bytes(2, "little"))

# sl427/decoder.py:382-393 —— 按"尾部 4B = 报警+状态"解析
alarm_bytes = data_field[-C.TP_LEN - 4:-C.TP_LEN - 2]
```

**构造性验证（已执行）**：按规范布局构造 81H 帧（`0100` 报警字 + 水位值 + `0000` 状态字 + Tp）送解码器：

```
水位 = 3450.001 m   ← 报警字节 01 00 被当作水位数据开头
工作交流电停电告警 = 正常   ← 真实报警位（bit0=1 停电）丢失
```

**影响**：与真实 RTU 的 81H 告警帧互通时，参数值与报警状态**双双解析错误**；编码器产出的 81H 帧同样不被合规中心站接受。
**注意区分**：82H（人工置数，7.5.3 b"数据域参照自报实时数据 7.3.22"= 参数+报警+状态）与 C0H 代码顺序**正确**，唯独 81H 错误。

## 三、中等缺陷（Medium）

### [M-1] `sl651/encoder.py:256-265` — 0x4A 设置时钟帧双重错误

**规范依据（表67，原文 2828~2842 行）**：设置遥测站时钟（4AH）下行正文**仅 流水号(2B) + 发报时间(6B)**，且"6 字节 BCD 码，YYMMDDHHmmSS，**作为校时时钟**"——校时值就是帧内发报时间字段本身。

**代码**：

```python
def build_clock_sync_body(self, dt=None):
    return datetime_to_bcd(dt)          # 正文里再塞 6B 时间 → 正文 14B
# 而 build_frame() 中 tx_time = datetime_to_bcd(datetime.now())  ← 发报时间是当前时间
```

**验证（已执行）**：`build_clock_sync_frame(datetime(2030,1,2,3,4,5))` → 帧内发报时间 = `2026-07-17 13:16:17`（编码时刻），正文长度 = 14（应为 8）。

**影响**：按表67 取"发报时间"校时的 RTU 将校到编码器当前时间，用户传入的 `dt` 被置于正文多余字节中，行为依赖厂商容忍度——校时功能实质失效。

### [M-2] `sl651/encoder.py:229-240` — 0x37 查询帧正文违规附加要素标识符

**规范依据（表42，原文 1998~2008 行）**：37H"查询遥测站实时数据"下行正文**仅 流水号 + 发报时间**（查所有要素）。编列要素标识符的是 **3AH**"查询指定要素实时数据"（表48）。

**代码**：`build_query_body` 附加 `引导符+定义符(0)` 列表 → 正文 12B（已实测）。

**影响**：严格按表42 实现的 RTU 将视其为畸形帧；代码实际需要的是 3AH 语义却用了 37H 功能码。需求 §2.2 将 0x37 标注"查询要素"同属误导。

### [M-3] `sl651/encoder.py:267-274` — 0x48 恢复出厂帧缺 98H 标识符

**规范依据（表63，原文 2725~2740 行）**：恢复出厂（48H）下行正文 = 流水号 + 发报时间 + **恢复遥测站出厂设置标识符**（附录 D.4 序号 121 = **98H**），且 6.6.4.22 强调"应与标识符配合使用以提高安全性"。

**代码**：`build_reset_body()` 返回空 bytes → 正文仅 8B（已实测）。

**影响**：以标识符作安全校验的合规 RTU 将拒绝执行恢复出厂；该下行命令在严格实现下失效。

### [M-4] `sl651/encoder.py:56-60,79` — 流水号规则两处违反规范

- 规范 6.6.2.4（原文 1381 行）："由中心站发起的**下行报文流水号为 0**"；
- 规范 6.6.4.2（原文 1463 行）：链路维持报"流水号采用**最后一次数据报文的流水号，且不累加**"。

代码对所有帧（含下行帧与 2F 链路维持报）统一 `_next_serial()` 自增。依赖流水号判重/判活的平台可能出现异常判定。

### [M-5] `sl427/encoder.py:178-194` — 84H 自报电压帧附加 11 字节多余数据

**规范依据（7.5.5，原文 1465~1469 行）**：84H"自报帧的数据域 **2 字节**，低位在前，高位在后……单位为 V"；附录 B 表 B.98 自报帧**不含 Tp**（确认帧才含）。

**代码**：电压 2B + alarm(2B) + state(2B) + Tp(7B) → 数据域 13B，L=20（已实测；合规帧 L 应=9）。

**影响**：按 B.98 解析的中心站将在第 3 字节起错位，CS 校验位置错误而丢弃帧。解码侧对合规 2B 帧碰巧兼容（走 else 分支），风险主要在编码侧。
附注：规范 7.5.1 表52 通式（含 Tp）与 B.96/B.98（不含 Tp）存在内部矛盾，附录 B 为具体帧结构定义，应采 B.98；83H 同理（代码未实现 83 编码，但 `constants.py:132` 声明其含 Tp，见 L-12）。

### [M-6] `sl427/decoder.py:369-373` + `encoder.py:131-138` — B0 响应帧尾部 4 字节状态字未处理

**规范依据（7.3.22，原文 1145 行）**：查询实时值响应帧"数据域**最后 4 个字节是终端机报警状态和终端机状态**"。

**验证（已执行）**：构造合规 B0 响应（水位 4B + 报警 2B + 状态 2B）：

```
水位 = -0.345 m      ← 正确
水位 = 0.000 m raw=00000000   ← 幻影要素：报警/状态字被当作第二个水位
```

解码侧尾部 4B 未剥离也未按 7.3.14 解析；编码侧 `build_query_response` 同样未附加报警/状态字。真实设备 B0 响应必现幻影要素。

### [M-7] `sl427/constants.py:103` + `decoder.py:134-154` — 综合参数（0x0E）三处错误

规范表45：综合参数位图 D7~D0 = 雨量/水位/流量/闸位/气象/功率/土壤含水率/水质。

1. **bit0（水质）永不解析**：`_parse_comprehensive` 从 `range(1, ...)` 起跳，注释"bit0 为综合参数自身标识"在规范中无依据。bit0 置位时水质漏解，且 offset 不前进导致**后续全部要素错位**（已实测：bit0+bit1 置位仅解出"土壤含水率"且数值错误）。
2. **COMP_BITS[3] = 0x08（电量）应为 0x07（气象）**：D3=气象。（v1.7 L-4 曾以"映射不完整"降级，实测可导致数据错位，升级为 M。）
3. **上行 1110B = 统计雨量被误当综合参数**：规范表6/7.5.6 c 规定上行 C0/81/82 中类型码 1110B 为统计雨量（1B 雨量类型 + 3B 雨量数据），代码 `decoder.py:356,390` 对上行帧也调 `_parse_comprehensive`。

### [M-8] `sl427/encoder.py:206` — PW 密码编码格式与规范表9 不符

规范 6.3.3.7 表9：PW 2 字节 = 第 1 字节高半字节**密钥1（BCD，0~9）** + 低半字节与第 2 字节共 12 位**密钥2（BCD，0~999）**。
代码：`pw.to_bytes(2, "little")`（BIN 小端整数）。非零密钥时结构与规范不符，RTU 验证必然失败（pw=0 时全零碰巧可用）。即使修正格式，密钥算法仍需按规范"系统建设时约定"。

### [M-9] `sl427/constants.py:105-128` — 报警/状态位定义三处与规范 7.3.14 不符

| 位 | 规范 7.3.14 | 代码 | 结论 |
|----|-------------|------|------|
| 报警 D9 | **温度超限报警** | 缺失（bit8 直接跳 bit10） | 漏报 |
| 状态 D2 | IC卡功能 **0=无效 / 1=有效** | `{0:"开启", 1:"关闭"}` | 语义颠倒 |
| 状态 D3 | 定值控制 **0=退出 / 1=投入** | `{0:"开启", 1:"关闭"}` | 语义颠倒 |

（D4 水泵 0=启动/1=停止、D5 箱门 0=开启/1=关闭、D6 电源与规范一致。）

### [M-10] `sl427/decoder.py:101-131` — 流量（0x03）符号/单位未按表35 解析

规范表35：流量 5B，BYTE5 **D7~D6=符号（00B 正/11B 负）**、**D5~D4=单位（00B=m³/s，11B=m³/h）**；缺测用 `AAAAAAAAAA`（5×0xAA）填充。
代码对 0x03 套用水位表34 的 `_parse_signed_bcd`（末字节高半字节=F 为负）：负流量（BYTE5=0xC0 起，高半字节 0xC≠0xF）被判为正，单位位被计入数值，0xAA 填充未识别。水位（表34 半字节 F 符号）解析正确，问题仅限流量/水量。

### [M-11] `simulator/engine.py:120` — `station_type` 默认值遮蔽站点自带类型

```python
def add_station(self, station, ..., station_type: int = 0x48, ...):
    encoder = SL651Encoder(..., station_type=station_type or station.STATION_TYPE)
```

默认 `0x48` 为真值 → `or` 回退**永不触发**。API 直调 `add_station(RainStation(...))` 不传 station_type 时，雨量站（0x50）/墒情站（0x4D）帧正文 F1F1 后的测站类别恒为 **0x48（河道）**。规范 6.6.2.6"遥测站地址与遥测站分类码是固定组合"。CLI 两条路径显式传值故被掩盖（v1.8 修 C-1 时的副作用：死参数变成了强制覆盖参数）。

### [M-12] `tests/test_round1_blindspots.py` — 5 项用例恒失败，长期无人运行

实测运行结果：**失败 5 项**。

1. `test_hourly_roundtrip_12:28`：`e.code.startswith("f")` —— 解码器输出的要素 code 为大写 `"F5"`，小写 `f` 恒不匹配 → `f5_count=0` 恒失败（用例自身大小写错误）。
2. `test_sl427_84_voltage_values:135`：查找 `name == "电池电压"`，解码器 84H 要素名为 `"电压"` → 4 个电压值用例全部"未找到要素"恒失败。

该脚本自入库起即为红色，需求文档与 v1.7/v1.8 报告均未覆盖其运行状态。失效测试资产的危害在于：**它名义上覆盖了 81/82/84/小时报盲区，实际从未产生有效拦截**——本次 C-2/M-5 恰在其"覆盖"范围内。

## 十、结语

1. **HEX/BCD 上行链路依然稳健**：CRC、定义符、负数 BCD、要素表、帧结构经逐条复核与 48 条真实报文验证无误；v1.7/v1.8 修复项全部保持。
2. **本轮 14 项 C/M 缺陷有共同方法论根源**：所有测试帧均为项目编码器自产，解码器只需"理解自己"即可通过测试。规范符合性必须以规范文本为源构造**异源测试向量**方能验证。
3. **优先级建议**（仅供参考）：C-1/C-2 影响协议制式与告警互通，应最优先；M-1~M-3 三个下行控制帧影响运维命令可达性次之；M-12（修复 round1 用例并纳入例行运行）成本最低、可防止回退。
4. **本报告仅审计，未修改任何源文件**。
