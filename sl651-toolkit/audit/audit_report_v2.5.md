## 三、中等缺陷（Medium）

### M-1 SL651 多包 SYN 路径完全绕过逐包 CRC 校验；残留包可跨报文交叉重组出「CRC 合法」的错误数据

**位置**：`sl651/decoder.py:347-402`（`_handle_syn`，包缓存前无逐包 CRC 校验）、`:404-426`（`_build_reassembled`，对合并正文**重算** CRC 并写入合成帧）、`:265`（`_pending` 缓存无淘汰）。

**规约依据**：SL651-2014 §6.3.2.5、表22——每个 SYN 分包帧自身是完整帧结构（起始符~结束符），CRC16 覆盖本包全部字节。逐包 CRC 是链路误码检测的唯一手段。

**问题描述**：

1. **逐包 CRC 从未被校验**。`feed()` → `_handle_frame` → `_handle_syn` 直接将 `body_slice` 写入 `_pending`，全程未计算/比对包自身 CRC。重组完成后 `_build_reassembled` 为合成帧**重新计算** CRC 并写入帧尾，随后 `decode()` 校验的正是这个新算出的 CRC——恒真。整条 SYN 链路上没有任何一处校验过原始逐包 CRC，传输误码字节无感进入水文数据。
2. **跨报文交叉重组**。`_pending` 按 `(is_ascii, center, station, pwd, func, direction)` 键缓存未完成序列，无超时、无 seq==1 重置启发。规约 SYN 包头（表22）仅有「包总数/序列号」，无报文标识字段，因此**不同报文的同号包无法从协议层区分**：报文 A(total=3) 的 seq1/seq2 缓存后 seq3 丢失，下一条报文 B(total=3) 仅 seq3 到达，即触发 `A1+A2+B3` 的错误组合；该正文经 CRC 重算后合法通过，无任何告警。仅当新序列重发**全部**槽位时才能靠覆盖自愈，丢包场景（正是多包机制针对的场景）必然留下污染窗口。

**实际验证**：

```
# 问题1：对包1 正文翻转 1 比特（该包 CRC 已失效）后与正常包2 重组
$ python3 -B -c "...corrupt = bytearray(p1); corrupt[0] ^= 0x01..."
带误码的包1 + 正常包2 ->
  解出报文: 1  crc_ok = True  warnings = []
  要素: [('39', '00012345'), ('38', '1260')]
  -> 逐包 CRC 从未被校验，误码字节被当作有效数据重组

# 问题2：A.seq1/A.seq2 缓存后，B(total=3) 仅 seq3 到达
=== 交叉重组结果 ===
解出报文数: 1
CRC_OK = True            （组合 A1+A2+B3 的错误正文，CRC 重算后必然通过）
elements: [('39', '00012339')]
warnings: []
```

**影响范围**：中心站/长连接流式场景下，传输误码与报文重发交错都会**静默产出带 `crc_ok=True` 标记的错误水文数据**——比拒帧更严重，因为它会带着「校验通过」的假象进入入库/告警等下游环节。STX 单帧路径的 CRC 校验（`crc_ok` 如实反映）不受影响。

**漏报原因**：`test_sl651_multipacket.py` 的重组用例均使用 CRC 正确的包，且只断言「重组成功」；变异测试对 SYN 帧只断言「仅抛受控 DecodeError」，无法发现「误码包被静默接受」。

**修复建议**：
1. `_handle_syn` 缓存前校验本包 CRC16（覆盖 `frame[:etx_pos+1]` 与帧尾 2B 比对），失败丢弃（或降级为单包告警）；
2. 重组合成帧时**保留逐包校验结果**：任一包校验失败则在 `DecodedMessage.crc_ok=False` 或写入 `warnings`，重算 CRC 仅作为合成帧可被 `decode()` 复用的实现细节；
3. 增加防御性启发式：`seq==1` 到达且该键已有缓存 → 视为新序列重置；组级超时淘汰（依规约重发节奏建议 5~10 分钟）；
4. 回归测试断言：含误码包的重组帧不得产出 `crc_ok=True` 的报文；跨序列残留包不得产出成功重组。

### M-2 SL427 综合参数：array 型功能码遇 0xAA 填充块会「吃掉」下一参数的数据块（同块展示两次，错位不传播）

**位置**：`sl427/decoder.py:193-213`（`_parse_comprehensive`）与 `:81-149`（`_parse_ctrl_func_data`，填充跳过逻辑位于 `:101-109`）。

**规约依据**：SL427-2021 行 1172「如仪表只监测其中一类参数，则另一类参数值用 `AAAAAAAAAA` 代替」——填充块是规约**合法输入**；表45 规定综合参数按位图定长定位（每个 bit 对应固定 `byteLen` 的数据块）。

**问题描述**：`_parse_comprehensive` 对每个置位 bit 调用 `_parse_ctrl_func_data(func, chunk, max_items=1)` 后固定 `offset += item_len`。当该块为全 `0xAA/0xFF` 且功能码是 array 型（COMP_BITS 中 0x0A 水质、0x03 流量、0x02 水位）时，`_parse_ctrl_func_data` 会 `continue` 跳过填充块、把**下一参数的数据块**当作本参数的值解析；而 `offset += item_len` 独立于其内部消费量推进，因此：

- **错位不传播**：后续参数的定位不受影响、无块丢失；
- 实际症状为：该填充参数与下一参数**展示同一块数据**（且因两者 signed/decimal 语义不同，可能算出不同数值），产生「两个参数同一个值」的误导输出；
- 若填充块是**最后一个**置位参数，则被静默省略（与 L-1 同源表现）；
- 全程不写 `warnings`。

`_parse_ctrl_func_data` 中「跳过填充继续找下一个有效值」的语义对真数组（N 个同类值）是正确的容错；但综合参数是**定长定位块**布局，跳过即取错块。两种布局语义共用同一函数导致冲突。

**实际验证**（构造 CRC 正确的 AFN=B0、func_code=0x0E 帧；bit5=流量(5B)、bit6=水位(4B)、bit7=雨量(3B)，块序与位序一致）：

```
# 无填充基线：
流量/水量 = 1.000  raw=0010000000
水位      = 4.321  raw=21430000
雨量      = 100.0  raw=001000

# 流量块=0xAA×5 填充时：
流量/水量 = 4.321  raw=2143000050   ← 错误吃掉水位块 + 雨量首字节
水位      = 4.321  raw=21430000     ← 定位仍正确（错位不传播）
雨量      = 100.0  raw=001000       ← 定位仍正确
warnings: []

# 雨量块（最后）=0xAA×3 填充时：雨量要素静默省略（不输出、不告警）
```

**影响范围**：现场仪表对未接入参数回填 `0xAA`（规约明确允许）时，综合参数自报/查询响应中的 array 型填充参数（水质/流量/水位）会**展示下一参数的数值**（两个参数同值、或与真实工况不符），末尾填充参数被静默省略；其余参数定位不受影响。误导运维判断。

**漏报原因**：v2.4 M-1 的影响分支清单未包含综合参数数据路径；`test_sl427_comprehensive_offset`（0xAA 填充后偏移正确）只构造了填充块在末尾/全填充的场景，未构造「array 型块在前、数据块在后」。

**修复建议**：`_parse_comprehensive` 不应委托数组语义——按 bit 定位切出**恰好 `item_len`** 的块：块为填充时输出 `-`（或跳过该要素）并写 `warnings`，然后无条件 `offset += item_len`。即把「定位块解析」与「数组解析」拆成两条路径。回归测试须断言相邻参数的 `raw` 互不相同。

### M-3 `feed()` 流式健壮性：`_pending` 无淘汰无上限（内存无界增长），坏帧三型异常行为（静默丢弃/流阻塞/跨帧拼接吞帧）均无错误通道

**位置**：`sl651/decoder.py:265`（`_pending`/`_pending_meta`）、`:272-290`（`feed` 的 `except DecodeError: continue`）、`:347-402`（`_handle_syn` 缓存逻辑）。

**问题描述**：

1. **内存无界增长**。未完成的 SYN 序列按键缓存，无超时、无组数/字节数上限。理论放大：每键可缓存 4095 包 × ≤4092B 正文（12 位 body_len 含 3B 包头）≈ 16MB；键空间随（伪造的）站址无界扩展。
2. **坏帧无错误通道，且行为分三型**。`feed()` 对异常帧无计数、无回调、无日志——调用方完全无法感知链路质量（对比：CRC 失败的帧会以 `crc_ok=False` 返回，尚有痕迹）。三类结构性坏帧行为各不相同：
   - **少报正文长度**：`decode()` 抛 `DecodeError` → `except DecodeError: continue` **静默丢弃**（好帧保留）——本报告初版仅描述了此型；
   - **谎报正文长度且缓冲不足**：`_extract_frame` 恒返回 `(None, 0)` 等待凑齐 total → **整条流阻塞**，后续合法帧全部滞留，不经过 `except` 路径；
   - **谎报正文长度且缓冲凑齐**：跨帧拼接出垃圾帧并正常解码（实测 `crc_ok=False`、帧长 65B > 实际 46B），**吞并下一合法帧的头部字节**，导致好帧丢失。

**实际验证**：

```
# 注入 3000 帧「仅含 seq=1、total=4095」的 SYN 帧（每帧 4000B 正文、站址递增）：
已喂 1000 帧: pending 组数=1000
已喂 2000 帧: pending 组数=2000
已喂 3000 帧: pending 组数=3000
_pending 缓存正文总量 ≈ 11.4 MB（无超时/无上限淘汰，约 3.9KB/帧 持续滞留）

# (a) 少报长度 + 好帧同批：解出 1 条（坏帧被 except 丢弃，好帧保留）
# (b) 谎报长度 + 好帧同批：解出 1 条，crc_ok=False、帧长=65（跨帧拼接的垃圾解码，好帧头 19B 被吞）
# (c) 谎报长度（仅坏帧）：解出 0 条、缓冲滞留 46B（流阻塞）；再喂好帧后拼接解出 1 条
```

**影响范围**：长驻的中心站接收进程在链路质量差（大量丢包/干扰）或收到恶意序列时，内存线性增长直至耗尽；同时链路异常对上层完全不可观测。

**修复建议**：
1. `_pending_meta` 增加时间戳，组级超时淘汰；对 `_pending` 总字节数/组数设上限（超限淘汰最旧组）；
2. `feed()` 增加错误上抛通道：`on_error` 回调或 `dropped_frames` 计数属性（保持现有返回值不变，向后兼容）；
3. `_extract_frame` 对「首帧声称 total 但缓冲已溢出该 total」的情形增加重同步判定（当前会跨帧拼接垃圾解码并吞并后续帧），谎报长度型坏帧不应无限等待；
4. 文档明确：多包键含站址，跨站共享单实例会串组——当前 web/CLI 均为单请求实例，属使用约束而非现实缺陷，但需写明。

### M-4 `CTRL_FUNC_MAP[0x0D]` 语义错位：报警或状态参数自报被解析为「电压」

**位置**：`sl427/constants.py:160-164`（`CTRL_FUNC_MAP[0x0D]` 及其注释）、`sl427/decoder.py:913`（C0 数据路径按功能码分发）。

**规约依据**：SL427-2021 表5/表6（规约行 492-532）——1101B（0x0D）**上行/下行均为「报警或状态参数」**；1110B（0x0E）下行=综合参数、**上行=统计雨量**（规约行 1505「当控制域C的命令与类型码为1110B时,自报数据为统计雨量格式」）；规约行 1319「控制域C中命令与类型码为1101B(报警或状态参数)」。

**问题描述**：`CTRL_FUNC_MAP[0x0D] = {"name": "电压", byteLen: 2, decimal: 2}` 的「电压」语义仅对 AFN=84H 成立（该路径有专用分支，不受此表影响）。任何携带 0x0D 类型码的 C0/B0/81/82 数据域——按 §7.3.14 应为**报警状态 2B + 终端状态 2B**——都会被当作 2B BCD 电压解析，剩余 2B 丢弃。另：0x0D 条目下的注释「上行: 统计雨量 (7.5.6 c)」有误，那是 0x0E 的上行语义（0x0D 上行即报警或状态参数）。

**实际验证**（C0 自报 func=0x0D，数据域=报警状态 0x0001（交流停电）+ 终端状态 0x0002）：

```
电压              = 0.01  raw=0100    ← 报警状态被当作 2B 电压 BCD
（终端状态 2B 被丢弃；帧级 alarm/state 字段与数据域语义完全脱节）
```

**影响范围**：表24「数据自报种类」含「报警或状态」项——设备按规约配置该自报种类后，其 C0+1101B 自报帧在中心站被解析成无意义的电压值，真实的报警/状态信息丢失，误导运维判断。

**修复建议**：0x0D 的名称与解析按上下文区分——上行自报（C0/81/82/B0）按 §7.3.14 解析为报警状态+终端状态（或复用 `_parse_alarm`/`_parse_terminal`）；AFN=84H 专用分支保持电压语义；同步修正 constants.py 注释（统计雨量属 0x0E 上行）。与 M-2/L-1 同属「命令与类型码/填充语义」域，建议一并收敛修复。

## 四、轻微问题（Low）

- 两个解码器对 CRC 失败**不拒帧**、只置 `crc_ok=False`：对调试工具是合理设计，但应在 README 明确「自动入库流水线必须检查 `crc_ok`」。

## 十、审计师评估

1. **协议核心算法持续稳定**：CRC16/MODBUS、CRC8/0xE5、BCD、定义符、帧结构、SL427 控制域/地址域/Tp、F4/F5 HEX 语义（本轮专项核对规约附录C 原文）均无算法级错误。
2. **最严重缺陷（M-1）**：多包重组是本轮唯一系统性风险——逐包 CRC 从未校验 + 无报文标识导致的跨序列污染，二者叠加使「CRC 校验通过」在 SYN 路径上失去意义。修复时须同时落地逐包校验、结果保留、seq==1 重置启发与超时淘汰四件事，只补其一仍会留缺口。
3. **M-2/M-4 延续了 v2.4 的教训**：填充/语义容错已连续两轮出现「同源路径未回扫」。建议把填充判定下沉为 `_parse_ctrl_func_data` 的统一前置语义（按布局参数区分「跳过」与「占位」），并把 `CTRL_FUNC_MAP` 的名称/解析按上下文（AFN、方向）参数化，一次性收敛，辅以「相邻参数 raw 互异」「0x0D 自报帧输出报警语义」的回归断言。
4. **M-3/L-2 属上线前置项**：`feed()` 面向长驻接收进程，内存上限、错误通道、谎报长度重同步、废弃方言一致性应在接入生产前解决；纯调试场景（CLI/Web）暂不受影响。
5. **建议下一轮优先处理**：M-1 > M-2 > M-4 > M-3 > L-1/L-2 > L-3/L-5/L-9 > 其余 Low。
6. **方法论建议**：
   - 凡「合成/重算校验值」的实现，必须显式保留并上报原始校验结果；
   - 同一解析函数被两种数据布局复用时，应参数化布局语义而非在分支内隐式兼容；
   - 多包/分帧类状态机必须定义三件事：超时、上限、重置条件——规约没给的，实现要补；
   - 常量表（如 CTRL_FUNC_MAP）中同一代码在规约不同表格/方向下语义不同时，映射结构应按上下文参数化，而非取单一名称；
   - 对外异常类型（EncodeError/DecodeError）应跨包收敛，避免调用方依赖异常类型时静默漏接；
   - 配置入口（YAML/CLI）应在装载期完成全部类型与进制校验，失败即退出并给出可读报错，而非进入运行循环后被宽泛异常处理吞掉。
