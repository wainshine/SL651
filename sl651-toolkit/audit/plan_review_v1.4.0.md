## 一、七个裁决点的裁决结果

### Q1 —— 裁决：同意收窄，上下文矩阵正确，予以放行

独立核验的规约证据（行号以 `水资源监测数据传输规约SL427-2021.txt` 为准）：

- **表5（下行，行 482）/ 表6（上行，行 516）**：1101B 的规范名双向均为「报警或状态参数」；1110B 上行=统计雨量（行 517）。
- **§7.3.22 n)（行 1310-1319）**：「查询监测终端机输入电压实时值：电压值数据为 2 个字节压缩 BCD 码……数据域 2+4 字节……控制域 C 中命令与类型码为 1101B（报警或状态参数）」——规约**自己把 0x0D 复用**为 B0 电压查询响应的类型码。
- **表 B.73（行 2675-2685）**：B0 响应帧无 Tp/PW，D + CS。当前 B0 解析路径（尾部 4B alarm/state + 其余按功能码）与规约一致，不应改动。

正确的心智模型是「**AFN + 类型码** 二元组决定数据布局」，而不是「类型码单独决定」。WP-4 的矩阵即该模型的正确展开。补充确认：AFN=84 专用分支（表 B.98，无 Tp）不受影响。

**一处事实性修正（不改变修复设计，但影响验收脚本对照）**：方案 §3 Q1 称「审计复现用的是 4B 短数据域，走的是短帧降级分支」——**不成立**。v2.5 M-4 与审计 B 的复现均为**足额长帧**（D=4B + alarm 2B + state 2B + Tp 7B = 15B ≥ 11，走 C0 正常分支），`_parse_ctrl_func_data(0x0D, real_data)` 在正常分支内把报警状态 2B 解成了电压。方案 WP-4 的「real_data 非空 → 原始摘要 + warning」恰好覆盖该用例，修复设计无需改动；但 §3 的定性应改正，否则检查点 1 的验收对照会对不上。

### Q2 —— 裁决：采纳保守方案，且应将其从「退路」升级为「主方案」

独立核验的规约证据：

- **表 B.63 / B.96（AFN=61/83 图片帧，行 2562-2572、2954-2964）**：帧结构 = 68 L 68 C A AFN **D(图片数据) CS 16H**——无 PW、无 Tp。规约唯一明确描述分帧的场景（§7.3.17c，行 1104-1105：图片分帧、DIVS 倒计数至 1 为末帧）**恰好完全无 AUX**。
- **表 B.75（B1 固态存储响应，行 2697-2707）**：无 Tp。**表 B.73（B0 响应）**：无 Tp。
- **表 B.100（C0 自报，行 3002-3013）**：D + Tp。规约**从未描述 C0/81/82 的分帧**，Tp 是否每帧重复无任何条文依据。

裁决：**重组仅对无 AUX 的 AFN（83/61/B0/B1/84）启用；C0/81/82 的 DIV=1 帧安全降级 + warning**。「Tp 只在末帧」只能作为待验证假设记录在 handoff，不得作为实现依据。这与方案的保守退路一致，但鉴于规约明文描述的分帧场景全部无 AUX，保守方案就是正确方案，不存在「确认后切换」的时间压力。

**两项方案未覆盖的规约风险，必须在 WP-2 开工前处理**：

1. **§6.3.3.2b（行 397）：「图片数据流的字节总数为 L×1K」**——AFN=83/61 帧的 L 语义可能不是「用户区字节数」而是 1K 块数。若如此，WP-2 的 `_extract_frame`（`total = L + 5`）对图片帧会**系统性算错帧长**。MF-3 用工具自身假设构造 83 帧属于自洽循环，证明不了真实语义。要求：实现前用真实 83 样本核验；无法核验前，AFN=61/83 同样走保守降级，MF-3 标注「L 语义待真实样本确认」。
2. **DIVS 计数起点歧义**：行 436「采用 BIN 码倒计数（255~1）」字面可读作「从 255 起倒计」（则分帧总数 N 未知）或「从本报文分帧总数 N 起倒计」。WP-2 的组装条件「要求 1..N 连续且 N == len(cache)」在前一种读法下**永不满足**。改为：**DIVS==1 触发组装，按 DIVS 降序拼接**；max DIVS 与 1 之间存在缺号 → error，不输出。

**一项细化**：`div==1 且 divs==1` 的帧是自含的（倒计数在首帧即到达 1），不应一律空要素——应正常解析 + warning「可能为分帧末片，多帧报文请使用 feed()」。MF-8 需拆为「divs>1 降级」与「divs==1 可解析」两个用例。

### Q3 —— 裁决：接受「有界 + 可观测」，不要求同批次严格模式

理由：同批次严格模式会废掉 `feed()` 的跨批次流式能力（正是该 API 的存在意义）；C3 契约（坏包不入缓存）+ seq1 重置 + TTL + 上限已把混组窗口压缩到「TTL 内的丢包+交错」，且 `reassembled/packet_count` 使产物可观测。**建议追加一个廉价启发**：同一 seq 再次到达但内容不同（比较字节而非仅覆盖）→ 重置该组 + warning——这能抓住「重发序列与残留组交错」这一主要混组路径，成本一行哈希比较。残余风险文档化即可。

### Q4 —— 裁决：同意最小闭环；解码侧建议限定启用范围

6.6.3.3b 的适用语是「**遥测站目的地地址**（如短信接收号码等，且不可能是负数）」——A 补齐是地址类参数的特权，不是通用 BCD 规则。方案「首半字节 A 且其余合法 → 按 A 补齐 + warning」对**任意 BCD 型要素**生效，会把普通要素的畸形数据也按地址语义解读。两个可接受口径中，建议取严：`allow_a_pad` 仅在 40H~43H 配置帧解析路径启用（附录D 参数所属域），定时报等要素路径保持拒绝（`-`，无 A-pad 解读）。编码侧 `a_pad_guides` 显式指定、不自动猜——同意。附录D 全量映射留 Roadmap——同意。

### Q5 —— 裁决：同意「默认全遮 + --show-raw」

一处表述修正：现状 `center_addr[:2] + "**"` 不是「空操作」而是**假脱敏**——`center_addr` 恒为 2 字符，`[:2]` 恒等，实际输出 `25**`（全显 + 装饰星号），比不脱敏更具误导性。修复方向（全遮）不变、更必要。排障影响可接受：`--show-raw` 覆盖交互场景；建议脱敏后的原始报文行保留「帧长 + 功能码」以便与输入关联（如 `7E7E…（46 字节，func=0x32，已脱敏）`）。

### Q6 —— 裁决：同意最小闭环（文档 + 一次性 warning + Roadmap）

理由：paho-mqtt 是新依赖 + 重连/线程模型 + 测试桩，属 v1.5 变更；当前暴露面（本机进程列表可见密码）与调试工具的威胁模型匹配。方案与追踪矩阵一致。

### Q7 —— 裁决：同意 v1.4.0 + 三处默认行为变更

- `encode_address` 默认值与校验：方案取 `110000 ≤ admin_code ≤ 829999`（GB/T 2260 省码 11~82，行 523-525），比审计 B v2.6 L-1 建议的下界（<10000，解码器边界充要条件）更严但**有规约依据**，同意。注意同步检查 examples/tests 中既有 `admin_code` 小值用法。
- `mode`/`heartbeat` 严格化：同意。`heartbeat` 限 `HEART_MAP`（0xF0~0xF2）有常量表依据；`mode` 限 0~3 有 §7.2.4 依据。
- 版本 v1.4.0：`feed()`/`divs=` 为新增 API，minor 合理。若 Q2 保守方案落地（仍是新增 API），**不降级为 v1.3.3**。

## 三、方案需修正的 4 处技术问题（按开工顺序）

1. **WP-2（开工前必须）**：§一 Q2 的两项——`_extract_frame` 对 AFN=83/61 的 L 语义风险（§6.3.3.2b）、DIVS 组装规则改为「DIVS==1 触发 + 降序拼接 + 缺号报错」。另加 divs==1 自含帧细化。
2. **WP-4（P2 前）**：§3 Q1 对 v2.5 M-4 复现路径的定性改正（足额长帧、正常分支，非短帧降级）。
3. **WP-10（P5 前）**：`function_code` 白名单 `{0x30,0x32,0x33,0x34,0x35}` **过宽**——0x34 小时报正文为 F4/F5 数组结构（表36）、0x35 人工置数为 F2+载荷（表38），而 `StationRunner._run`（`engine.py:62`）恒用 `build_timing_frame` 构造正文。允许这两个值会发出「CRC 合法但正文结构错误」的帧。收紧为 **{0x30, 0x32, 0x33}**（三者正文同构，规约表28/表34），或按功能码路由到对应 body 构造器。
4. **WP-1（P1 内）**：逐包 CRC 校验只写了二进制布局（`frame[:-2]` vs `frame[-2:]`）；ASCII SYN 帧（含 L-2 修复后的旧方言 0101 路径）CRC 为末尾 4 个 ASCII 字符，需同样校验。补一句实现说明即可。
