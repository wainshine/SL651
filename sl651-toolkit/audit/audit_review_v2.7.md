## 二、新增 M-2c（v2.7 漏报）：SL651 SYN 单包的 16 位长度没有被解析

v2.7 M-2a 只验证了“每包 2525B、合计 5050B”的重组上限，但没有验证**单个 SYN 包自身 >4095B**。这是更前置的解析问题：

- 表22（规约行 1208-1211）：SYN 帧的“报文上下行标识及长度”为 2B，“表示 SYN 控制符之后、结束符之前的报文字节数，用 HEX 编码，**允许长度为 0001H～FFFFH**”。
- 当前 `sl651/decoder.py:390,395` 两处都按 **12 位**取长度：

```python
body_len = ((buf[11] & 0x0F) << 8) | buf[12]
```

- 因此长度 5003（0x138B，3B 包头 + 5000B 正文）的合法 SYN 包被当成 924B：`_extract_frame` 只取出 924B，尾部 CRC 自然不匹配，整包被丢弃。

**实测**（按表22 手工拼 5000B 正文、CRC 正确）：

```
frame len 5020, feed 输出 0 条
errors=['丢弃 924B 无法解析帧: SYN 包 CRC 校验失败: 接收=0x4141, 计算=0x95A4']
dropped_frames=1
```

即：**即使把重组改成“分片集合直接进解析管线”，只要 `_extract_frame`/`_handle_syn` 仍按 12 位读长度，单包 >4095 的合法图片/固态存储报文依然进不来。** M-2 的修复建议必须加两条：

1. SYN 帧长度按 16 位读取（注意表22 的 2B 长度与 STX 帧的“方向位+12 位”布局不同）；
2. `_max_frame_bytes` 当前为 4124，需按 SYN 上限（65535+帧头）调整，否则读取 16 位后仍会被上限拒绝。

建议 v2.7 将 M-2 拆为：
- **M-2a**：SL651 重组合计 >4095 被合成单帧上限拒绝；
- **M-2b**：SL427 重组 >255 被合成单帧 L 拒绝；
- **M-2c（新增）**：SL651 SYN 单包 16 位长度被按 12 位解析，单包 >4095 无法进入重组。

M-2c 的可观测性更差：不是“重组后丢弃”，而是“CRC 失败”这一误导性错误（用户会以为链路误码）。

## 三、M-1 的两处精确性问题

### 3.1 ASCII 不是 3 处错码，而是 4 处语义错配

规约与当前 `SL651_ASCII_ELEMENTS` 对照：

| 规约 | 规约含义 | 当前代码 | 问题 |
|---|---|---|---|
| `NS` | 19H 开机台数 | `MT` = 开机台数 | 键错（应 NS） |
| `SW` | 32H 输沙量 | `SW` = 剩余水量 | 值错（应输沙量） |
| `SQ` | 44H 含沙量 | `SQ` = 输沙量 | **值也错**（应含沙量） |
| `SD` | 规约不存在 | `SD` = 含沙量 | 多余键（应删除） |

v2.7 写“3 处错码（SD→SQ、MT→NS、SW→输沙量）”，但 **`SQ` 当前也是错的**；如果修复者按字面“把 SD 改名为 SQ”，会与现有 `SQ` 冲突。正确修法应显式写成：

```
删除 SD；SQ=含沙量；SW=输沙量；NS=开机台数；删除 MT；
剩余水量改用 SYL1~SYL8（60H~67H）
```

### 3.2 表 C.1 行数与缺项

58H~75H（30 项）+ FDH 缺失、`SL651_ELEMENTS` 仅 101 键、文档称“101 项已全部收录”——这些均属实。表 C.1 尾部确实到 75H，FDH 为 DATA，76H~EFH 保留、FFXXH 自定义；131 个要素行的口径成立。

## 四、L 项的对抗性核对

| 项 | 复核 |
|---|---|
| L-1 | 实测 `ST 00418D2337 4B`；喂 `K` 得 `('K','未知')`；真实 |
| L-2 | 代码 `.isdigit()` + `int(pkt[0:3])`；表18 明确 HEX；真实；`00A001` 会被判 total=0 |
| L-3 | 实测切在 30/33 字节分别得 1/2 个要素、`warnings=[]`；**“2 要素”不是固定数字**，但“部分数据无告警”成立 |
| L-4 | 规约 N(6,1) 与代码/文档 N(5,1) 不符；数值上限 99999.9（3B/1 位小数）本身正确；文档级 |
| L-5 | `center: "2"` 实测 TypeError；真实 |
| L-6 | B1 帧实测落「未知功能码 AFN=0xB1」；真实 |
| L-7 | 84 D=3B 实测只输出 12.34V、无 warning；真实 |

L-1/L-2 可以合并为“ASCII 路径规约符合性”一组；L-4 纯文档；L-6/L-7 是解析完整性/降级留痕问题，Low 合理。

## 五、对严重度的对抗意见

1. **M-2 不应只写“重组上限”**：M-2c（单包 16 位长度）是更前置的 Medium；只修“合成单帧”而不修 `_extract_frame/_handle_syn`，图片/固态存储单包 >4095 仍不可用。
2. **M-1 仍然成立**，但“3 处错码”应改为“4 处键值错配（含 SQ 当前错值）”，否则修复清单会漏掉 `SQ` 的正确含义。
3. **L-3 的“2 要素”应改成“部分要素（数量取决于切分点）”**；不改变 Low 定级，但报告应避免把构造相关数字写成固定事实。
4. **L-1/L-2 的定级 Low 可接受**；如果项目把 ASCII 作为生产路径，L-1 可升 Medium，但当前定位是调试/模拟工具，Low 合理。
