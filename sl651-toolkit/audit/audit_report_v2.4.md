## 三、中等缺陷（Medium）

### M-1 缺测填充处理不完整：状态/事件/水泵/中继等子解析仍将 `0xAA`/`0xFF` 当作有效值

**位置**：`sl427/decoder.py:240` `_parse_alarm`、`:253` `_parse_terminal`、`:521`（AFN=5D 事件记录）、`:501`（AFN=5F 水泵数据）、`:510`（AFN=60 引导码长）、`:553`（AFN=63 中继状态）；AFN=57/58 尾部 4B 状态切分位于 `:433` `_parse_query_response`。

**规约依据**：SL427-2021 正文明确 `0xAA` 为「未采集/无数据」占位——规约行 1172「如仪表只监测其中一类参数，则另一类参数值用 `AAAAAAAAAA` 代替」；规约行 900「若无备用信道，备用信道类型码和中心站地址码为 `0xAAAA`，共 2 个字节」。

**问题描述**：v1.3.1 为修复审计 v2.3 M-2，新增 `_safe_bcd_le` 并在 `_parse_query_response`/`_parse_control_response` 的 BCD 数值分支（50/53/55/56/57/58/59/5A/62/64/96 等）做了填充容错。但同一响应帧中的**非 BCD 数值分支**仍直接解释填充字节：

- `_parse_alarm`/`_parse_terminal` 对 `0xAAAA` 按位展开，输出「全部告警」等误导性状态；
- AFN=5D 事件记录用 `int.from_bytes` 把 `0xAAAA` 显示为计数 `43690`；
- AFN=5F 水泵数据把 `0xAAAA` 显示为电压/电流值 `43690`；
- AFN=60 引导码长把 `0xAA` 显示为 `170 s`；
- AFN=63 中继状态按 `0xAAAA` 位图输出「A机故障/B机正常」等；
- AFN=57/58 仅数据体做了填充降级，**尾部 4B alarm+state** 仍按位展开。

**实际验证**（构造 CRC 正确的上行响应，数据域为规约允许的 `0xAA` 填充）：

```
$ python3 -B -c "from sl427 import SL427Decoder, SL427Encoder, encode_address, make_ctrl; ..."
AFN 5E: [('工作交流电停电告警', '正常'), ('蓄电池电压报警', '电压低'), ('水位超限报警', '正常'), ...]
AFN 5D: [('事件记录[数据初始化记录]', '43690'), ('事件记录[参数变更记录]', '43690')]
AFN 51: [('站点时钟', '无效时间(AAAAAAAAA...')]
AFN 63: [('中继自动切换/自报', '0xAA'), ('中继状态[工作机A机]', '故障'), ('中继状态[工作机B机]', '正常'), ...]
```

整帧未被拒（对比 v2.3 前的 `DecodeError` 已有改善），但输出被填充字节污染，且**不写入 `warnings`**。

**影响范围**：现场设备对「未采集」参数回填 `0xAA`/`0xFF` 时，Web/CLI 会展示与真实工况不符的告警、计数、电压电流等，误导运维判断。

**漏报原因**：
1. v1.3.1 的定向回归测试 `test_fill_response_tolerance`（`tests/test_sl427_query_afn.py`）只断言「不抛异常 + 存在要素」，未校验 5D/5E/5F/60/63 等分支的**值语义**；
2. 变异测试以「仅抛受控 `DecodeError`」为通过标准，无法发现「合法帧被解释为错误值」。

**修复建议**：在 `_parse_alarm`/`_parse_terminal` 及各子解析入口统一复用填充判定（全 `0xAA` 或全 `0xFF` → 输出 `-` 并写入 `warnings`）；AFN=57/58 的尾部状态同理。

### M-2 AFN=84 自报电压帧遇 `0xAA` 填充仍抛 `DecodeError`

**位置**：`sl427/decoder.py:943`（`_parse_data_field` 的 AFN=84 分支），`:946` `bcd_bytes_to_int_le(data_field[:2])`。

**规约依据**：同 M-1（规约行 1172/900）；AFN=84 数据域为 2B BCD 电压（表 B.98）。

**问题描述**：v1.3.1 已为查询/控制响应引入 `_safe_bcd_le`，但 AFN=84 自报电压分支仍直接调用 `bcd_bytes_to_int_le`，非法半字节（含 `0xAA`/`0xFF` 填充）抛 `ValueError`，经 `decode` 包装为 `DecodeError`，导致**整帧被判为解码失败**。

**实际验证**：

```
$ python3 -B -c "from sl427 import SL427Decoder, SL427Encoder, encode_address, make_ctrl; ..."
84 AA -> RAISED DecodeError 报文解析失败: 无效 BCD 字节: 0xAA
```

**影响范围**：设备在电压未采集时回填 `0xAA` 的合法自报帧会被拒，与其他分支的填充容错行为不一致。

**漏报原因**：v2.3 M-2 的影响分支清单未包含 AFN=84；v1.3.1 的 `test_sl427_84_no_tp` 只验证有效电压，未构造填充。

**修复建议**：AFN=84 分支改用 `_safe_bcd_le`，`None` 时输出 `-` 并写入 `warnings`。

## 十、审计师评估

1. **协议核心算法稳定**：CRC16/MODBUS、CRC8/0xE5、定义符、负数 BCD、帧结构、SL427 控制域/地址域/Tp 经 14 轮审计 + 48 条真实报文验证，未发现算法级错误。
2. **最严重缺陷（M-1）**：v1.3.1 对 v2.3 M-2 的修复只覆盖 BCD 数值分支，同类填充在状态/事件/水泵/中继等分支仍被当有效值，属「定点修复未回扫同源路径」的典型漏报；建议以统一的填充判定函数收敛所有子解析。
3. **一致性问题（M-2）**：AFN=84 电压帧的填充拒帧与 M-1 同源，修复时应对所有直接调用 `bcd_bytes_to_int_le` 的路径统一替换为 `_safe_bcd_le`。
4. **建议下一轮优先处理**：M-1（填充完整性，影响面最广）> M-2（AFN=84 一致性）> L-1/L-2（文档一致性）> L-3/L-4/L-5。
5. **方法论建议**：
   - 修复一处填充/异常契约后，**回扫同一函数族的所有分支**，避免局部修复；
   - 定向回归测试须断言**值语义**（`-` / `warnings`），而非仅「不抛异常」；
   - 变异测试增加「合法帧不得抛异常、合法填充不得产生错误值」的正向断言；
   - 文档计数（测试项/组数/测站数）应在发版时由脚本从实际运行结果生成，避免手工漂移。
