## 三、中等缺陷（Medium）——均为本轮新发现

### [M-1] `sl427/decoder.py:181-199` — 综合参数对 array 型参数贪婪消耗，后续参数被吞并产生幻影要素

**规范依据（表45）**：综合参数位图 D0~D7 = 水质/土壤含水率/功率/气象/闸位/流量/水位/雨量，每个置位参数在数据区**出现且仅出现一次**。

**代码**：

```python
# _parse_comprehensive: 对每个置位位，把"全部剩余字节"交给通用解析器
chunk = bytes(remaining[offset:])
sub_items = _parse_ctrl_func_data(func_code, chunk)   # array=True 的参数会循环吃光剩余
consumed = sum(e.byte_len for e in sub_items)
offset += consumed
```

`CTRL_FUNC_MAP` 中流量（0x03)/水位（0x02)/流速（0x04)/水质（0x0A) 均为 `array=True`，`_parse_ctrl_func_data` 对 array 型参数**按剩余长度循环解析**——这在 B0 单参数响应（同类型多值）语境下正确，但在综合参数（每型仅一次）语境下错误。

**构造性验证（已执行）**：bit5（流量5B)+bit6（水位4B)+bit7（雨量3B)，flag=0xE0，数据 12B：

```
项数: 2
  流量/水量 = 4030.201 m³/s       ← 正确
  流量/水量 = 100000.345 m³/s(0x01) ← 幻影：水位+雨量 9B 被当作第二个流量
  （水位、雨量要素丢失）
```

注：当后续参数总长度 < 当前参数 byteLen 时碰巧正确（如 流量5B+水位4B），缺陷具有隐蔽性——这正是一个"部分场景自洽"的错位 bug。

**影响**：B0 综合参数响应、FF 自定义综合帧中，凡 array 型参数后还有其他参数且剩余字节 ≥ 其 byteLen 的，解析结果必错。与真实 RTU 互通时数据错位。

**修复方向**（仅供参考）：`_parse_comprehensive` 应按 `definition["byteLen"]` 单值截取，或向 `_parse_ctrl_func_data` 传入 `max_items=1`。

### [M-2] `sl651/encoder.py:236-247` — 小时报 F4 雨量组按 2B/值编码，与真实设备（12B/12值）及自家解码器均不一致

**实测证据（三重矛盾）**：

1. **真实设备布局**：北京水务 34H 真实报文中 F4 定义符 = `0x60` → 数据 **12 字节**（1B/值 × 12 组，0.1mm）；福建 34H 同样 12 组 F4 可解析。
2. **解码器实现**：`_parse_f4_array`（`decoder.py:657-674`）按 **1B/值** 解析，与真实设备一致。
3. **编码器实现**：`build_hourly_body` 写 `_make_def_byte(24, 1)`（24 字节）且每值 `val.to_bytes(2, 'big')`（**2B/值**）。

**构造性验证（已执行）**：`build_hourly_frame(..., rain_amounts=[0..11])` 自产帧送自家解码器：

```
第1时段雨量 = 0.0 raw=00   ← 期望 0.0（碰巧）
第4时段雨量 = 1.0 raw=0A   ← 期望 3.0，实际读出第2个值的高字节
第6时段雨量 = 2.0 raw=14   ← 全部错位
```

**影响**：模拟器/编码器产出的小时报雨量组**不合规**（真实平台按 12B 解析将错位），且连自产自销往返都无法保真——v1.9 L-6 修复引入的新缺陷。现有测试（`test_hourly_frame_validation` 仅 14 要素计数、`test_hourly_roundtrip_12` 只查 F5）均未覆盖 `rain_amounts` 路径，故未拦截。

**修复方向**（仅供参考）：F4 改为 12B（1B/值，0.1mm，缺测 0xFF），定义符 `_make_def_byte(12, 1)`，并补充含雨量组的往返测试。

### [M-3] `sl427/decoder.py:392-409` + `constants.py:102` — 上行 C0/81/82 中 func=0x0E（统计雨量）仍误解析为"综合参数"，且吞掉后续字节

**规范依据（7.5.6 c）**：上行自报帧中类型码 1110B 为**统计雨量**，数据域 = 1B 雨量类型 + 3B 雨量数据。v1.9 M-7③ 指出了"误调 `_parse_comprehensive`"，本版修复仅移除了该误调用，但未实现统计雨量解析——`CTRL_FUNC_MAP[0x0E]` 仍是 `{"name":"综合参数","byteLen":1}`，通用解析器按 1B 单值解析首字节后**丢弃其余 3B**。

**构造性验证（已执行）**：C0 + func=0x0E + 数据 `01 23 45 00`（类型1+雨量3B）：

```
综合参数 = 1  raw=01   ← 名称错误（应为统计雨量），且 23 45 00 三字节被静默丢弃
```

**影响**：任何按规范上报统计雨量的 RTU，其 C0/81/82 帧中该参数解析结果名称与数值均错误，且 4B 数据只呈现 1B。属 v1.9 M-7③ 的**修复不全**。

**修复方向**（仅供参考）：上行方向 func=0x0E 走独立分支（1B 类型 + 3B 雨量，小端 BCD）。
