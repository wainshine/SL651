## 三、中等缺陷（Medium）

### M-1 SL427 分帧报文（DIV=1）不重组、不告警：分片被当完整报文解析，末帧产出垃圾告警位图、C0 分片产出垃圾时间/告警/状态

**位置**：`sl427/decoder.py:830-837`（`_decode_inner` 对 `ctrl["div"]==1` 仅 `offset += 1` 跳过 DIVS 字节）、`:933-951`（B0 分支按 `raw_len>=4` 截取 alarm/state）、`:901-931`（C0 分支按 `raw_len>=11` 截取 Tp/alarm/state）、`sl427/encoder.py:94-141`（`build_frame` 无 DIVS 参数，编码/解码布局不对称）。

**规约依据**：SL427-2021 §6.3.3.1c「正文/用户数据区字节总数超过最大传输单元，应分帧发送」；§6.3.3.3.3「拆分标志位 DIV=1，表示此报文已被拆分为若干帧，**接收后应拼接**。此时发送帧与确认帧的控制域 C 为 2 个字节，增加的一个字节表示拆分帧计数 DIVS，采用 BIN 码倒计数（255~1），当 DIVS 为 1 时表示最后一帧」；§7.3.17c「当图片分帧传输时……直至中心站接收拆分帧计数 DIVS 为 1 时表示最后一帧」。表3 表明每个分帧均携带完整 C(2B)+A(5B)+AFN 头部，数据域 D 为本帧分片。

**问题描述**：解码器对 DIV=1 的帧：

1. **不重组**：各帧数据域分片从不拼接，`DIVS` 倒计数被完全忽略（连「是否末帧」都不区分）；
2. **每片独立解析且静默出错**，分三种形态（均已实测）：
   - **中间分片**（数据域 < 4B，如 B0）：解析为空 `elements=[]`、`warnings=[]`——数据无痕丢失；
   - **末帧**（B0，数据域 = 数据残片 + alarm 2B + state 2B）：`raw_len>=4` 判定通过，把「上一帧数据残片的尾字节」与 alarm 首字节**拼成 2B 错位位图**展开为 14 项告警要素——产出**貌似合法的垃圾告警**（本次复现中甚至碰巧给出与真实告警相同的「停电」结论，极具迷惑性），真实雨量值丢失，`warnings=[]`；
   - **C0 中间分片**（数据域 ≥ 11B）：`raw_len>=TP_LEN+4` 判定通过，把局部数据的**尾部 7 字节截为「观测时间」、再往前 4 字节截为 alarm/state**——实测产出 `水位=3020.100 / 7060.504`、垃圾告警、垃圾时间，`warnings=[]`。
3. **编码侧同样不支持且与解码侧不对称**：`make_ctrl(div=1)` 可产生 DIV=1 控制字，但 `build_frame` 不会追加 DIVS 字节；这样的帧交给自家解码器会被按「C 为 2B」吞掉 AFN 后错位解析。即分帧路径编码/解码两头都不通，且互相误解。
4. 触发场景真实存在：L 上限 255 字节，超过即应分帧——图片自报（AFN=83，§7.3.17c 明确按分帧传输）、固态存储历史数据回传（AFN=B1）、大 N 的水位/水压上下限响应（AFN=57/58）都会走到。当前工具对这类报文要么无痕丢数据、要么给出错误值。

**实际验证**（构造 CRC 正确的两帧 B0 分片 + 一帧 C0 分片，完整复现脚本见报告附注）：

```
# 完整单帧（对照）: D = 雨量3B + alarm2B(停电) + state2B
  雨量 = 102.5，告警「交流停电=停电」——正确

# 分帧1(DIVS=0x02, 雨24前2B) + 分帧2(DIVS=0x01, 雨尾1B+alarm+state):
  帧1: elements=[], warnings=[]            ← 雨量前 2 字节无痕丢失
  帧2: 无雨量要素；告警状态由「雨量尾字节+alarm首字节」错位拼成 2B 位图展开 14 项
       （0x00,0x01 → 0x0001 → 「交流停电=停电」——碰巧与真实值同、字节来源完全错误）
       warnings=[]                          ← 无任何「分帧未重组」提示

# C0 分片(仅 20B 局部数据, DIVS=0xFF):
  水位=3020.100 / 水位=7060.504 / 垃圾告警 / 垃圾观测时间, warnings=[]
```

**影响范围**：任何超过 255B 用户区的上行报文（图片/固态存储/大 N 参数响应）在中心站侧被静默误解：中间分片无痕丢失、末帧产出错误告警位图与错误要素值、C0 分片产出垃圾时间与垃圾水位。相比拒帧，这类「带合法帧结构外观的错误输出」对运维与入库链路危害更大。

**漏报原因**：15 轮历史审计的焦点在 HEX/BCD 帧、填充语义、SYN 多包（SL651 侧）与流式解析，`parse_ctrl` 返回的 `div` 字段从未被当作独立路径检查；测试套件（含变异测试）从未构造过 DIV=1 帧。

**修复建议**：
1. 解码器实现分帧重组：按（方向、地址域、AFN、func_code）分组缓存分片，DIVS 倒计数，收到 DIVS=1 时按序拼接各帧 D 后整体解析（结构可参照 SL651 侧 `_handle_syn`，但须吸取其教训——见 v2.5 M-1：缓存需上限/超时/逐帧 CRC 已验，拼接后不得重算校验值遮蔽原始校验）；
2. 在重组实现落地前，**保守降级**：`div==1` 的帧不产出数据要素，写入 `warnings`「分帧报文未重组（DIVS=xx），已忽略数据域」——宁可少给，不可错给；
3. 补编码侧对称性：`build_frame` 增加 DIVS 参数（div=1 时控制域 C 扩为 2B），或在 `make_ctrl` 文档明确分帧不被支持并拒绝 div=1；
4. 回归测试：两帧分片重组结果与完整单帧解析逐字段一致；中间分片不得产出任何要素。

## 十、审计师评估

1. **协议核心算法持续稳定**：CRC16/MODBUS、CRC8/0xE5、BCD、定义符、帧结构、综合参数位序（本轮逐位核对规约表45）、45H 状态位语义（逐项核对表58）均无算法级错误。
2. **本轮最重要的发现（M-1）属于「能力边界」缺陷**：前 15 轮审计都在检查「已实现路径是否正确」，本轮转向「规约要求但未实现的路径如何表现」——结果发现最危险的正是后者：分帧重组、A 补齐 BCD、负数数组这些「工具不支持」的规约合法输入，全部走了**静默误解**而非**显式拒绝**。建议项目把「不支持的合法输入必须可观测地拒绝（warnings/EncodeError）」写进 project.md 的全局契约，与「畸形数据被拒绝」契约并列。
3. **修复优先级建议**：M-1 > L-1/L-5（往返矛盾类，修复成本低收益高）> L-2/L-3（契约完备性）> L-4/L-6 > L-7/L-8。v2.5 的 4M（尤其 SYN 逐包 CRC）仍应先于本轮 Low 处理。
4. **两条横向规律（连续多轮成立，建议制度化为修复验收标准）**：
   - **同源判定必须单点实现**：填充判定（三轮残余）、地址方式判定（L-1）——凡解码器有一个判定逻辑，编码器必须调用同一函数或共享常量，禁止两侧各写一套前置条件；
   - **降级必须留痕**：所有「无法正确解析」的分支（填充、数据不足、分帧、A 补齐、位宽不符）统一走「`-` + warnings」或抛错，禁止「空输出/错位输出/吞字节」三型静默行为。
5. **方法论**：本轮新增「构造性回放不依赖项目自测代码构造帧」的做法（手工按规约表3/表22 拼帧），避免了像第一轮抽查那样被项目构造习惯（build_frame 固定 STX）误导——建议后续审计延续「按规约拼帧」而非「按项目拼帧」。
